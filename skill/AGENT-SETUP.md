# 首次运行 / 初始化记忆存储 手册（Agent 版）

**当用户第一次在你的宿主上运行 `/checkpoint-memory`、问"记忆根目录设在哪"、或者要求你"装一下/检查一下记忆"时，按本手册执行。**

你处在一个特殊位置：你能比用户快得多地检查机器、运行验证工具、读取已有笔记——但你也是最容易搞砸的组件：把宿主没有的能力说成有，或者好心去"修复"别人根本没让你碰的记忆。本手册就是拦住这两件事的流程。按顺序走。

- **这不是协议本体**——运行期的召回/写入/策展规则在 [`SKILL.md`](SKILL.md)，那个在安装之后每次任务都生效。
- **这不是给人手装看的**——本机已有 `./memory/` 时，普通首次运行只需"确认落点 + 打勾"，见 §2 和 §3。

## 先读这十行

它们放在最前面，是因为这些失败都发生在头一分钟、还没人读到这里。违反其中一条是你运行流程的缺陷，不是判断取舍。

1. **绝不猜测宿主能力。** 证据不足 → 报告 `unknown` 并问。
2. **读之前先声明；写之前先停下。** Gate 1 是声明后继续看；Gate 2 是硬停（下一节）。
3. **不要改已有笔记。不批量改，也不"就这一条"。** 早于本协议建成的记忆，笔记经常没有日期、没有 `Why:`/`How to apply:`，这是正常且被接受的现状，不是缺陷清单。把它们报告为*可接受的遗留偏差*，除非用户逐条、看到内容后要求，否则别动——你本来也补不齐：文件 mtime 不等于事实最后成立的时间，只有用户知道一条笔记为什么值得留。**更别把它们说成"损坏"。** 有遗留笔记的存储是在正常工作。诸如"不健康""没完全装好""90% 正确""让我修好再复查"这类词，会把一个外观上的小口子变成紧急事故，逼用户在不知情的情况下授权改自己的历史。如果一切正常、没坏任何东西，答案就是"它能用"——遗留笔记提一次，作为可无限期忽略的可选清理。
4. **绝不复述笔记正文；读得越少越好。** 数数、结构、上限检查由索引和 frontmatter 回答；为了确认"有五条"就把每条都展开读完，对私人笔记毫无收益。不读不行的情况也有，那没问题；读超出问题所需的部分才是有害的——因为读到的一切都进你的上下文，对托管的模型就是出口流量，而且正文一个字也不会进你的报告。
5. **默认不要扫描 home 目录。** 改成问候选路径；真要广扫，单独获批并限定范围。
6. **存在 ≠ 已配置 ≠ 已生效 ≠ 已核验。** 永远不要把四者坍缩成"已安装"。
7. **单写者。** 绝不在别的 agent 拥有的存储上再挂一个写者。
8. **失败就报告为失败。** 附上显示它的工具输出。
9. **偏离默认不等于缺陷。** 装好的配置常*故意*偏离文档默认——刻意精简的规则片段、非标准的存储路径、被环境变量抬高的上限。报告你观察到的，然后**问是否刻意**。绝不自作主张改回默认；那可能造成实害（把用户故意精简的片段恢复成全量，会重新撑大每一次的提示词）。
10. **回答你能回答的。** 你抛回给用户的每个问题都在消耗他们的注意力。如果一项检查便宜、无破坏、且在获批范围内，就跑掉并报告结果——不要把它列成需要用户去解决的未知项。

## 两条 Gate

两条 Gate **不是同一种东西**，混为一谈会毁掉整个流程。

| | 是什么 | 你做什么 |
|---|---|---|
| **Gate 1 — 勘察** | 一次**声明** | 说明范围，然后**直接去看** |
| **Gate 2 — 写入** | 一道**硬停** | 列出精确改动，等一句"可以" |

**Gate 1 不拦你。** 说明你要读什么、不读什么，然后继续做，不要停下来等许可。这是刻意的：
- 只读勘察不改变任何东西。风险在*读了什么*——由收窄范围（规则 5）和绝不复述正文（规则 4）来控制，而不是靠先问一句，那只是把同样的读取延迟而不是避免。
- "帮我装一下"本身已隐含"先看看我的机器"。不看不装。
- 在这里卡住有比多读坏得多的失败模式：只要没人应答（批处理、CI、用户走开了），整个流程产出就是**零**。一份不带任何发现的礼貌提问，比没有手册还糟。

所以：**声明、勘察，然后把发现和开放问题一起放到用户面前。** 即使永远没人应答，报告也独立成立——而且你的任何东西都没被动过。

**Gate 2 是真正的停。** 没有用户批准一份具体清单，你的任何东西都不能变。没人应答时，正确的结局是"未安装 + 一份报告"，而不是你自己拍板装了。

## §1 记忆根目录：可复现的决策顺序

检测到"未配置 `CHECKPOINT_MEMORY_ROOT`、无 `.memory-path`、`./memory` 不存在"时，**默认落点已经是明确的**，不需要开放提问。按此顺序走：

1. **先找已存在的存储**（这是优先项；提议新建是最后手段，不是默认）。检查本宿主适用的位置：
   - `./memory/`（本协议默认，见 SKILL.md §1）
   - 早前安装留下的 `.engramory-memory/` 或旧记忆目录
   报告你找到的（含大小、条数），一条一句问用户"这是你的那份吗？"——**不要**开放式问"你的记忆存哪？"，那是把活儿推回给用户。
2. **确实没有，才提议新建**，并明说"这会**新建**一个存储，不是采纳已有的"。默认值是**工作目录下的 `memory/`**——SKILL.md §1 白纸黑字的默认，不是需要用户选出来的选项。你要做的只是**给出这一个落点**、说明影响，请用户**打勾确认**。
3. **写入前路径必须经用户确认**。无论新建还是采纳，任何东西写入之前都要确认。

**不要把这些当成并列选项罗列**，更不要放任用户两难：给一个"已有存储"的用户再塞一个新路径，会得到**两个**存储——旧的被弃、新的为空、记忆悄悄分裂在两边。这种失败很安静，比不装还糟。而"当前所在目录"往往是最方便的提议，却几乎从不是正确的那个。

**禁止硬编码绝对路径**（SKILL.md §1：`never hard-code an absolute path`）。默认值是相对的 `<project-root>/memory/`。

### Git 相关

- 若 `<MEMORY_ROOT>` 落在 git 仓库内，**必须 git-ignore**——记忆带机器本地又非凭据的敏感细节（IP、ssh 路径、序列号）。创建 `memory/` 时若在 git 仓库里，同步补上 `.gitignore` 条目，并确认为用户同意。
- git 只用于判断"什么不该写"和验证指针；**记忆更新永远由模型手动策展，任何自动流程都不得代刷**（见 SKILL.md §1 / rules-snippet）。

## §2 归属与边界：写之前先确认两件事

两道都是承重墙，先讲清再写：

- **归属。** 你来写这份存储，还是另有 agent 拥有、你只从它读取？协议假设**单写者、多读者**，没有锁。往别人的存储上再挂一个写者，是损坏性 bug，不是配置偏好。只读接线才是对该 store 的正确做法。
- **隔离。** 如果 dsh 或其他宿主*管理自己的*记忆并自动写文件，`<MEMORY_ROOT>` 必须指向**独立文件夹**——两个不同家规的写者会在同一批文件上打架。复用宿主目录，只有当它真是"用户控制的一堆普通文件"时才正确。

## §3 首次运行的实际回应方式

用户问"记忆根目录设在哪"时，正确回应不是把问题抛回去，而是：

> 检测到未配置 `CHECKPOINT_MEMORY_ROOT`、无 `.memory-path`、`./memory` 不存在 → 依协议默认将落在 **`<项目根>/memory/`**。我将创建 `memory/`（含 `MEMORY.md` 索引），若当前在 git 仓库会同步加入 `.gitignore`。**确认？**

——**结论自己给出，只请用户打一个勾**，并顺手确认没有别的既有存储。

若无法读到机器（沙箱/容器/远程、看不到用户相关目录），任何"未找到"都要报告为 *"从当前执行环境不可见"*，**绝不**报告为 *"未安装"*——沙箱看不到 `~/.claude/` 不能证明用户笔记本上没有，报了假阴性会让人去重装已有的东西。

## §4 需要放下"是否合适"的候选场景

**提议装之前先问一次**"你想要的到底是不是策展式存储"——答案偶尔是"不"，现在说比装好后省太多。

本协议是**策展纪律**，为个人规模存储设计：单写者、值得在几个月后还留着的笔记、小到每次会话都能整份加载的索引。有些被称作"共享 agent 记忆"的东西其实是借了同一个词的不同东西：

- **逐轮协作日志**——每个 agent 追加自己刚做的事让下一个接着干。那是工作日志，要追加写、高频率、不判断什么值得活；本协议三者全相反。
- **多 agent 并发交接通道**——本协议假设单写者且无锁。
- **超出常载窗口的存储**——活跃集大过索引上限后，正确答案是检索系统而不是更大的索引。

这些都不是用户配置的失败，也不是把协议掰成日志的理由。明说你要的哪半被覆盖、哪半没有，让两者共存：项目里放一个非正式的协作 scratch 文件没问题，只要**不接进存储、不进 `MEMORY.md` 索引**——一旦进去，这里每一条规则都会开始跟它打架。

## §5 已存在时：先核验，别只报"已配置"

**"已配置"和"会触发"是两个不同的断言，只有后者对用户有价值。** 报告 `configured` 却没试过，等于把用户自己答不了的问题留给他——正是规则 10 要防的。

对已有的存储，跑只读健全检查：

```sh
python3 tools/doctor.py <MEMORY_ROOT> --no-schema
```

那个基线（超限索引、断指针、孤儿、重复 slug）就是结构基线。

**doctor 输出里的 `fix …:` 行是给人看的建议，不是给你的任务清单。** 它们说"什么*能*解同一个问题"，没说"该解、谁来解、现在解"。结构性问题（指针指向已消失的文件、两个同 slug 笔记）确实要有人决定；存量笔记缺 schema 字段不算——见规则 3。把这些提示当 backlog 抢着烧完，是本流程最常见的误用。

按四个状态分别报告每个组件，而不是一个笼统的"是/否"：

| 状态 | 含义 |
|---|---|
| **存在** | 文件/条目在 |
| **已配置** | 内容有效、指向正确的根和执行脚本 |
| **已生效** | 宿主的常载路径真的加载它 |
| **已核验** | 已端到端证明（见下） |

两个特别要防的坑：

- **半装看起来像装好了。** 常驻规则片段是主安装步，却最容易漏——有存储、有技能、有 hook，但规则文件里没那一段，纪律就不在常载路径上，普通任务可能完全不带它跑，存储慢慢积累一堆不合协议的笔记。**单独一行**报告它，绝不并进"已安装"；既要确认*文件*也要确认*文本*（宿主并不加载的规则文件里的片段 = 存在但不生效）。
- **存在但过时。** 旧版本留下的技能副本和 hook 脚本，默认是"保留"而不是"替换"。旧副本是"存在"，不是"已配置"。

还有一件四个状态都说不出的：**这个差异是不是故意的。** 精简的片段、不寻常的路径、抬高的上限——每个都像配置错误，每个也完全可能是正常选择。报告差异、说清代价与收益，然后**问**（规则 9）。未经询问就把文档默认改回去，不是修复。

## §6 上报：写给那个人

上面都是你的**诊断**，不是报告。来让你装的人通常不是项目作者，不关心状态表，问的就一句：*能用吗，我现在要做什么？* 回答这个问题。三板斧：

- **第一行就下结论。** 先说能不能用，不是你先检查了什么。
- **用他们的语言，不用我们的。** "索引用了上限的 78%" 而不是 `97 lines / 19.6 KB, under cap`。"那个防它无限增长的规则在工作，我测过了" 而不是 "cap hook verified"。别让人去查术语。
- **只讲会改变他们行为的发现。** 一条不导向任何决定或行动的发现，自己留着。把开放问题数说出来，并让它很小。

**尺寸用让下一步动作最明显的单位说**——百分比，或"大概还能塞 N 条"。没看过上限的人，`97 lines` 毫无意义。接近上限时要明说*接近*："under cap"在 40% 和 98% 读起来一模一样。

### 典型话术

**新项目首次运行、确认落点（最常见）：**
```
未检测到既有记忆存储。依默认将建在 <项目根>/memory/（含 MEMORY.md 索引）。
当前在 git 仓库内，会同步加 .gitignore 条目。确认？
```

**找不到 / 看不见（沙箱、未知宿主）：**
```
我从当前环境看不见你的真实机器，无法判断是否已有。
能麻烦你跑 `ls <记忆根>` 并把结果贴给我吗？
```

**已存在、一切正常：**
```
已装好且工作正常。我测过索引大小守卫，确实会触发。
你的记忆：N 条笔记，索引用了上限的 78%。没发现问题。
有件事想确认：你的规则文件用的是精简版纪律而不是全文。省提示词但漏了几条规则。是刻意的吗？是的话我保持不动。
```

**已存在但真的有问题的（规则片段没进常载文件）：**
```
已安装但不真正生效。
告诉我怎么维护记忆的那段规则从没进到你的常载文件里，所以它们没加载。
存储和大小守卫都正常——缺的是纪律本身，所以笔记一直在堆积却没按需要结构写。
修法是往常载文件贴一段。要我贴吗？（会往那个文件加约 40 行，别的不动。）
```

**保留细节，只在被问时交出。** 完整诊断——宿主证据与置信度、每组件四状态、`doctor` 输出、执行环境——留好，一句话提供（"要技术细节吗？"），需要时再给。绝不用它开头。
